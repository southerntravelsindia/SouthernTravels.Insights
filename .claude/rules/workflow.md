# Workflow rules

## Pick the path before you start

| Path | Use for | Gates |
|---|---|---|
| **Light** | A bug fix or small change inside one app: no schema/proc change, no auth/payment/money code, no new endpoint, ≤ ~3 files | Short plan in chat → implement → build → `/review` → PR |
| **Standard** | Features, reports, anything touching procs/schema, auth, payments, money, messaging, or more than one app | BA-approved FSD → test cases first (`/generate-tests --fsd`, QA) → plan (TSD) → tech-lead approval → `/db-change` if needed → implement on a branch → build/test → `/generate-tests` → `/review` → `/prepare-pr` → PR with sign-offs |

If a "light" change turns out to touch anything in the Standard column, stop and switch paths. When the user asks for a Standard plan, use it even if the change looks small.

## Where the documents live

`<docs>` is the `docs` path in `.claude/kit/kit.json` (docs-claude). Templates are in `.claude/kit/templates/`.

| Document | Owner | Path | Template |
|---|---|---|---|
| FSD (what and why) | BA; approved by the BA lead | `<docs>/planned/specs/<ID>.md` | `fsd-template.md` |
| TSD (how: the approved plan) | Developer; approved by the tech lead | `<docs>/planned/tsd/<ID>.md` | `tsd-template.md` |
| Contract between repos | API developer | `<docs>/planned/contracts/<ID>.md` | `contract-template.md` |
| Test plan (cases traced to FSD and TSD, written test-first from the FSD; QA records results) | QA; generated by `/generate-tests` | `<docs>/planned/tests/<ID>.md` | `test-plan-template.md` |

Older specs may still be under `<docs>/planned/reports/`. Check the catalog row's Spec column first.

## Planning a Standard change

Plan in plan mode (or in chat with no edits) before any code. For heavy reading, use read-only research agents so the main session keeps its context.

1. **Spec gate.** Read the FSD. If it is missing, still Draft, or not merged in docs-claude, **stop**: say what is missing, using `fsd-template.md`, and offer to draft it for the BA. Don't plan from a catalog row or a chat message alone.
2. **The plan follows `tsd-template.md`**: requirement → implementation mapping (every field, filter, total, CTA and export to an endpoint, method, proc and column, each marked *verified* or *proposed*), impacted code with `path:line`, DB objects, cross-app callers, risks against the security checklist, numbered BA questions, milestones each with its own verification, and the test strategy. If the test plan exists, read it and map its test IDs to the milestones. Cite the FSD version it was planned from.
3. **Databases.** List every proc or table touched and say "/db-change needed for: …". Don't design the SQL in the plan.
4. **Other apps.** List callers in other repos of any route, DTO or proc that changes (the "HTTP calls" sections of the other apps' `data-access.md`, and the procedure docs' Apps column).
5. **Stop for approval.** After the tech lead approves, offer to save the plan to `<docs>/planned/tsd/<ID>.md` on a `docs/claude-<id>-tsd` branch in docs-claude. A human opens the PR.
6. **Spec changes.** If the FSD's version is newer than the one the TSD cites, stop and re-plan the affected milestones before coding.

## Contracts between repos

- **API side:** when you add or change a route, request or response that another repo calls (e.g. the CostSheet UI), write or update `<docs>/planned/contracts/<ID>.md` from `contract-template.md` in the same piece of work. Keep changes backward compatible, or give the deploy order.
- **Caller side (UI, panels):** build API calls only from the contract file. If it is missing or wrong, stop and raise it against the API work; don't guess the shape from the API code.

## Always

- Work on a branch named per the **Branch convention** in this repo's CLAUDE.md. If it has none, use `<type>/claude-<ticket-or-date>-<short-name>`, e.g. `feat/claude-ins-02-ops-workload`. Every branch you create carries the `claude-` marker after the type; the guard hook blocks branch names without it. Never commit to `master` / `Master`; the guard hook blocks it.
- Read the app's `code-map.md` and `data-access.md` (paths listed in `CLAUDE.md`) before exploring from scratch.
- Plan before editing; get approval before touching schema, procs, auth, integrations or architecture.
- Implement in the main session, one approved milestone at a time. Build after each milestone and report the exact command and result lines.
- Keep edits minimal and reversible. Don't reformat, rename or "clean up" code outside the scope.
- Don't push, merge, deploy, or send messages; a human does that.
- When you learn something durable about the system (a business rule, a proc contract, a gotcha), propose an update to `docs-claude`.
